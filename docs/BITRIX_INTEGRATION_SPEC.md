# ТЗ: прослойка между мини-игрой «Сноуборд» и 1С-Битрикс

Версия: 0.1 (черновик). Поля **[ЗАПОЛНИТЬ]** заполняет бизнес. Поля **[РАЗРАБ]** решает Битрикс-разработчик.

---

## 1. Общая схема

```
┌─────────────────────┐   AJAX (JSON)   ┌──────────────────────────┐    D7 API    ┌──────────────┐
│  Игра (HTML/JS)     │ ──────────────▶ │  Прослойка на PHP        │ ───────────▶ │ Модуль sale  │
│  /local/games/snow/ │ ◀────────────── │  (контроллер + HL-блоки) │              │ (купоны)     │
└─────────────────────┘                 └──────────────────────────┘              └──────────────┘
```

- Игра — это статичный бандл (HTML/JS/картинки), без собственного бэкенда.
- **Игра ничего не решает про призы.** Она сообщает только «забег начат» и «забег закончен, собрано X монет и Y сундуков».
- **Прослойка решает**, положен ли приз и какой, проверяет лимиты, создаёт купон в `sale` и возвращает его игре для показа.
- Логику игры можно подделать в браузере, поэтому все проверки делаются только на сервере.

## 2. Что и когда выдаётся (предложение, бизнес подтверждает)

### 2.1 Кто может получить приз
| Параметр | Предложение | Решение |
|---|---|---|
| Нужна ли авторизация на сайте | Играть может кто угодно. **Приз выдаётся только авторизованному пользователю** (купон привязывается к `USER_ID`) | **[ЗАПОЛНИТЬ]** |
| Гость при попытке получить приз | Видит кнопку «Войдите или зарегистрируйтесь, чтобы забрать приз». Перед этим игра просит авторизоваться, чтобы не терять результат | **[ЗАПОЛНИТЬ]** |

### 2.2 Лимиты
| Параметр | Предложение | Решение |
|---|---|---|
| Забегов «на приз» в день на пользователя | 3 (дальше можно играть без призов) | **[ЗАПОЛНИТЬ]** |
| Максимум призов в день на пользователя | 1 | **[ЗАПОЛНИТЬ]** |
| Максимум призов за всю акцию на пользователя | 3 | **[ЗАПОЛНИТЬ]** |
| Период акции (даты, часовой пояс) | ДД.ММ – ДД.ММ, Asia/Almaty | **[ЗАПОЛНИТЬ]** |

### 2.3 Когда выдаётся приз (триггеры)
| Событие в игре | Что происходит | Решение |
|---|---|---|
| Игрок подобрал **сундук** и доехал до финиша | Сервер разыгрывает приз из пула (п. 2.4) с учётом лимитов | **[ЗАПОЛНИТЬ]** |
| Игрок собрал **монеты** | Монеты — это очки. *Опционально:* монеты копятся за всю акцию, и при 500 монетах выдаётся гарантированный купон | **[ЗАПОЛНИТЬ]** |
| Сундук не собран или игрок разбился | Приза нет. *Опционально:* утешительный купон 3% | **[ЗАПОЛНИТЬ]** |
| Лимит призов исчерпан | Сундук открывается, но показывает «Сегодня призы закончились, возвращайтесь завтра» | **[ЗАПОЛНИТЬ]** |

### 2.4 Пул призов
| Код | Приз | Тип в Битриксе | Вес (шанс) | Всего штук | Срок купона | Мин. сумма заказа | Ограничения |
|---|---|---|---|---|---|---|---|
| `D5` | Скидка 5% | Купон на правило корзины | 50 | ∞ | 14 дней | — | **[ЗАПОЛНИТЬ]** |
| `D10` | Скидка 10% | Купон | 30 | 1000 | 14 дней | — | |
| `D15` | Скидка 15% | Купон | 10 | 200 | 7 дней | | |
| `SHIP` | Бесплатная доставка | Купон на правило доставки | 9 | 500 | 14 дней | | |
| `GIFT` | Подарок к заказу | Купон на правило «подарок» | 1 | 50 | 14 дней | | |

**[ЗАПОЛНИТЬ]** Суммируются ли купоны с другими скидками? Какие категории или товары исключены?

Если приз закончился (`Всего штук` выдано), его вес обнуляется и розыгрыш идёт среди оставшихся.

### 2.5 Как пользователь видит приз
- Сразу в игре: название приза, код купона, кнопка «Скопировать», срок действия, кнопка «В каталог».
- **[ЗАПОЛНИТЬ]** Дублировать ли код на e-mail (почтовое событие Битрикса)?
- **[ЗАПОЛНИТЬ]** Показывать ли список полученных купонов в личном кабинете?

## 3. API прослойки (контракт с игрой)

Предлагаем D7-контроллер (`\Bitrix\Main\Engine\Controller`) и вызов через `BX.ajax.runAction`
или `fetch` с `sessid`. Конкретную реализацию выбирает **[РАЗРАБ]**. Имена ниже условные.

### 3.1 `snowgame.api.status` — состояние игрока (вызывается при загрузке игры)
Ответ:
```json
{
  "authorized": true,
  "promoActive": true,
  "attemptsLeftToday": 2,
  "prizesLeftToday": 1,
  "totalCoins": 340,
  "myPrizes": [{ "title": "Скидка 10%", "code": "SNOW-7KQ2-XM", "expiresAt": "2026-12-31" }]
}
```

### 3.2 `snowgame.api.startRun` — начало забега
- Проверки: акция активна, лимит попыток.
- Создаёт запись забега, возвращает `runId` (случайный, неугадываемый).

Ответ: `{ "runId": "b3f1…", "rewardEligible": true }`.
`rewardEligible=false` означает, что играть можно, но приза не будет (гость или лимит исчерпан).

### 3.3 `snowgame.api.finishRun` — конец забега
Запрос:
```json
{ "runId": "b3f1…", "coins": 57, "chests": 1, "score": 1840, "finished": true, "durationMs": 76120 }
```
Серверные проверки (антифрод):
1. `runId` существует, принадлежит этому пользователю и ещё не завершён (один `finish` на забег).
2. Прошло не меньше `MIN_RUN_SECONDS` (например, 60 с) с момента `startRun`.
3. `coins` ≤ `MAX_COINS_PER_RUN` и `chests` ≤ `MAX_CHESTS_PER_RUN`. Эти константы даёт разработчик игры.
4. Лимиты из п. 2.2 не превышены. Для лимитов используется блокировка или транзакция, чтобы два запроса одновременно не дали два приза.

Если всё в порядке и `chests ≥ 1`, сервер разыгрывает приз из пула (п. 2.4), создаёт купон и сохраняет выигрыш.

Ответ:
```json
{
  "prize": { "id": "D10", "title": "Скидка 10%", "code": "SNOW-7KQ2-XM", "expiresAt": "2026-12-31" },
  "attemptsLeftToday": 1,
  "totalCoins": 397,
  "message": null
}
```
или `{ "prize": null, "message": "Сегодня призы закончились, возвращайтесь завтра" }`.

### 3.4 Коды ошибок
`NOT_AUTHORIZED`, `PROMO_INACTIVE`, `LIMIT_REACHED`, `RUN_NOT_FOUND`, `RUN_ALREADY_FINISHED`, `RUN_TOO_SHORT`, `INVALID_DATA`.

## 4. Хранение данных (предложение, детали за **[РАЗРАБ]**)

Highload-блоки или собственные таблицы ORM:

**SnowGameRun**: `ID`, `RUN_ID`, `USER_ID`, `STARTED_AT`, `FINISHED_AT`, `COINS`, `CHESTS`, `SCORE`, `IP`, `USER_AGENT`, `STATUS`.

**SnowGamePrizePool**: `CODE`, `TITLE`, `DISCOUNT_ID` (правило корзины в `sale`), `WEIGHT`, `TOTAL_QTY`, `ISSUED_QTY`, `COUPON_DAYS`, `ACTIVE`.
Пул должен редактироваться из админки, чтобы маркетинг мог менять шансы без программиста.

**SnowGameWin**: `USER_ID`, `RUN_ID`, `PRIZE_CODE`, `COUPON`, `CREATED_AT`.

## 5. Выдача купона в `sale`

1. Маркетолог заранее создаёт правила работы с корзиной в разделе «Маркетинг → Правила работы с корзиной», по одному на каждый приз, с флагом «применяется только по купону».
2. Прослойка генерирует одноразовый купон, привязанный к пользователю, например:
```php
use Bitrix\Sale\Internals\DiscountCouponTable;

$code = DiscountCouponTable::generateCoupon(true);
$result = DiscountCouponTable::add([
    'DISCOUNT_ID' => $prize['DISCOUNT_ID'],
    'COUPON'      => $code,
    'TYPE'        => DiscountCouponTable::TYPE_ONE_ORDER,
    'MAX_USE'     => 1,
    'USER_ID'     => $userId,
    'ACTIVE_FROM' => new \Bitrix\Main\Type\DateTime(),
    'ACTIVE_TO'   => (new \Bitrix\Main\Type\DateTime())->add($prize['COUPON_DAYS'] . ' days'),
    'DESCRIPTION' => 'SnowGame run ' . $runId,
]);
```
*(Пример ориентировочный, разработчик сверит его с версией модуля.)*

Альтернатива: заранее сгенерировать пачку купонов и выдавать их из пула по одному.

## 6. Размещение игры

- Статичные файлы игры кладутся в `/local/games/snowboard/` (их передаём мы).
- Страница акции: `<iframe>` или компонент-обёртка с `<div id="snowgame">` и подключением бандла. Вариант выбирает **[РАЗРАБ]**.
- Если iframe лежит на том же домене, cookies и сессия Битрикса работают и авторизация видна.
- Адрес API игра берёт из конфигурации, например `window.SNOWGAME_CONFIG = { apiBase: "...", sessid: "..." }`.
